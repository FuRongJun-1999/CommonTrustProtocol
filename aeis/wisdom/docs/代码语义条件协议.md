# 代码语义条件协议（Code Semantic Condition Protocol）v1.0

> 状态：文档先行（GPT 2026-08 评审建议 + 荣 CCG 方向确认）
> 定位：**代码实现负责执行，中文语义注释负责声明条件，条件图负责索引，白箱负责路由。**
> 原则：代码不能只有「能运行的实现」，还必须拥有「可被白箱认知和路由的语义入口」。
> 与 CCG 闭合：注释=图的索引（名实），条件图=路由（条件→代码），白箱=执行/路由。
> 哲学映射：功能条件=条件空间（when）、子功能=结构（what parts）、执行方式=过程（how）、
> 不适用条件=盲区边界（when NOT——与盲区注册表同构）。

## 0. 四要素注释格式

每个函数/类/包的语义注释固定为四要素（标记词可兼容既有「生效条件/执行」）：

```python
def predict_routes(problem, context):
    """【功能条件】
    当问题需要根据已有知识寻找可执行推理路径时使用。
    输入必须包含待判断问题与当前认知上下文。

    【子功能】
    ① 识别问题对应条件空间
    ② 沿条件/因果边搜索候选路径
    ③ 条件约束过滤无效路径
    ④ 标记语义诱导路径及可信等级
    ⑤ 无法归属时返回结构性盲区

    【执行方式】
    先识别问题锚点，再沿条件/因果边递归搜索；
    对候选路径做条件约束验证，返回可执行路径及状态。

    【不适用条件】
    ① 输入不存在有效问题锚点时不调用
    ② 不负责修改知识图结构
    ③ 无法验证因果关系时不得将语义相似当作因果结论
    """
```

| 要素 | 标记（兼容） | 含义 | 图索引角色 |
|---|---|---|---|
| 功能条件 | 功能条件 / 生效条件 | 何时使用；输入/前置状态 | 条件节点（路由门槛） |
| 子功能 | 子功能 | 内部能力分解 | 子功能节点（结构检索） |
| 执行方式 | 执行方式 / 执行 | 步骤/调用/结果 | 执行词节点（机制检索） |
| **不适用条件** | **不适用条件**（新增） | 何时不能用；约束/边界 | **盲区节点（负路由）** |

## 1. verifier 检查

- R1 函数/类中文注释（已有）
- R2 注释中文语境（已有）
- R3 三要素标记（功能条件/子功能/执行方式——兼容 生效条件/执行）（已有，681 达标）
- **R4 不适用条件**（新增）：主函数注释须含「不适用条件」标记；
  自动生成草稿（参数边界/None 分支提取）+ 外部精修；升级期软模式，全库达标后开硬检查

## 2. 认知图集成（代码知识入白箱体系）

```
              认知图
                │
     ┌──────────┼──────────┐
     ↓          ↓          ↓
   理论知识    工程知识    代码知识（CCG）
                           │
                      函数/类/包
                           │
                  条件→子功能→执行→不适用
```

白箱遇工程问题「如何实现 X」：
```
问题 → 识别条件 → 查询注释索引（CCG）→ 定位函数/类/包 → 读取实际代码 → 执行/修改
```

## 3. 修改纪律（语义入口约束）

白箱修改代码时，**先改语义声明，再改实现**：
条件描述 → 子功能 → 执行路径 →（不适用条件）→ 实现
——语义与实现同改，索引不失效；CCG 重新建图后检索仍可达。

## 4. 自迭代闭环

```
中文注释 → 语义结构 → 条件图 → 代码定位 → 代码执行
    → 执行结果 → 预测误差 → 更新条件图/注释
```
代码维护纳入白箱自迭代闭环；「何时调用哪段代码」转化为条件识别问题。
