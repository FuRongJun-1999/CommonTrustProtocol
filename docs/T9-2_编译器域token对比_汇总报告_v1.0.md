## 〇、结论先行（一句话）

**在本测试（提示已完整的低认知负荷确定性任务）上，灵枢机制注入是强负收益：
总 token 9 倍（109,418 vs 12,117）、通过率更低（3/5 vs 5/5）——
失败 100% 源于「递归反思机制注入成为思考放大器」，每轮推理 token 超 6000 被截断，
可见程序被吃光。T9 一轮结论「任务定义质量是第一杠杆」再次验证：提示补全后裸 LLM 全部一轮通过。**

## 三、失败机制分析（B 组 18 轮失败诊断）

| 类别 | 次数 | 根因 |
|---|---|---|
| 结果错·结果未定义 | 14 | **推理截断**：每轮 completion 达 6000 上限（prompt+6000=6728/6819/6910…），可见输出为空或残缺（C/D 空 program、E 无结尾）→ VM 符号表无「结果」 |
| 运行错 | 1 | C-R4：`unsupported operand '+' float and str`（截断残缺程序） |

**截断机制**（探测实证）：B 组 system 含递归反思 preamble（元反思/全局视角/条件分析/验证指示），
deepseek-v4-flash 认真执行 → 每轮 reasoning 6,000+ token（A 组无 preamble，每轮 ~1,900）；
max_tokens=6000 时 reasoning 占满预算 → 可见输出被截断为空/残缺。

**对照实验**（提示补全后探测）：任务 A 裸 LLM total=694（reasoning 147）；任务 A 灵枢组
total=5,278（reasoning 4,497）——同样一轮过，机制组思考 30 倍于裸组。

## 四、过程修正记录（诚实归因：前两版结果作废）

| 版本 | 失效根因 | 修复 |
|---|---|---|
| v1 | max_tokens=2000 截断推理（一次调用 reasoning 3,160/3,211）→ 空程序假失败 | →4000 |
| v2 | 修正轮推理更长又截断；英文标识符 f/n；换行致函数体吞语句 | →6000 + 语法约束补「中文标识符/单行」 |
| v3（本报告） | 语法补全后裸 LLM 一轮过；灵枢组思考放大仍截断 | 数据有效，如实呈现 |

**任务定义质量迭代**（一轮结论再次验证）：语法约束从 4 条补到 8 条
（单行/中文标识符/阿拉伯数字/分支不赋值/无多余返回/递归终止条件…），
裸 LLM 从「5 轮全错烧 12K」变为「1 轮过 1.9K」。

## 五、附加发现：protocol-compiler 真实缺陷清单（测试中暴露）

1. **多行程序函数定义吞掉后续语句**：换行版程序编译 ok 但 VM 符号表空（换行后语句被并入函数体）
2. **空源码编译成功**：`compile_source("")` 返回 ok=True（应报错）
3. **条件分支作用域**：分支内赋值（临时值 = 一）分支外不可见（LOAD 报名实不符）
4. **顶层 返回 提前终止程序**：函数体外的 RETURN 使后续赋值不执行（语义上应报错或界定）

→ 均已在任务描述中规避/说明；缺陷 1/2 建议列入协议编译器修复队列（白箱自举验证主线素材）。

## 六、结论与方向修正

1. **本测试结论**：低认知负荷、提示完整的确定性微任务上，灵枢机制注入是**思考放大器**，
   token 9 倍、通过率更低。机制注入不是无条件免费的。
2. **方向修正**：灵枢机制（递归反思/全局视角/白箱查找）的价值场景是**需要真实规划与反思的复杂任务**
   （用户原意「鹈鹕骑自行车网页版」=规范长期企业级项目），而非 60 字符单行程序。
   下一步应设计**多约束/多组件/需要迭代设计**的任务（如「用中文编译器实现一个完整计算器程序：
   支持加/减/乘/除/括号优先级/多函数/结果缓存」），让「反思验证减少试错」真正有发挥空间。
3. **注入方式修正**：递归反思 preamble 应按任务复杂度**条件化启用**（简单任务不注入），
   且 max_tokens 需按推理模型特性重新配比（reasoning+输出预算分离）。

## 七、边界与诚实声明

- 单领域（中文编译器）5 任务 × 2 组，初步观察，非统计显著
- 两组同提示、同任务、同轮次上限（5）、同 max_tokens——唯一变量 = 机制注入
- 白箱注入只给单元名+语义要点（calibration），未给代码骨架
- 结论不否定灵枢机制本身，仅否定「无条件注入于简单确定性任务」的用法
