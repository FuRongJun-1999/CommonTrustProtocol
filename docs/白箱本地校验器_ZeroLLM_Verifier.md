# 白箱本地校验器（Zero-LLM Verifier）设计 v1

> 状态：文档先行（先设计，后实现，再验证）
> 背景：昨日 13 亿 token 实测，99.9% 是缓存命中（重复查表校验）。GLM 缓存命中价 2 元/百万，
> 按量 13 亿 ≈ 2,600 元/天；Coding Plan 更承载不了这个量级。
> 结论（荣 2026-08-25）：**把缓存命中全部本地化，彻底抛开大模型依赖**。
> 白箱负责代码编写已实现（六域 675 单元，零 LLM）；本设计补齐「校验器」环节。

## 0. 问题陈述

白箱自举代码训练期需要**外部校验**：白箱写的代码
① 是否符合规范（协议/语义对齐）② 是否能够执行（语法/样例/集成）。
当前校验依赖 LLM（重复查表 → 99.9% 缓存命中 → 巨额 token 成本）。
**目标：校验器白箱化、本地化、零 LLM，重复校验结果本地缓存。**

## 1. 架构总览

```
白箱生成的代码 + 单元定义（task/pattern/cases/校准基准）
        │
        ▼
┌─────────────────────────────────────────────────┐
│  本地校验器 verifier.py（零 LLM）                │
│                                                 │
│  ① 校验指纹 → 本地缓存（已校验过 → 直接返回）    │
│  ② L1 语法：ast.parse + 结构规则                │
│  ③ L2 样例：输入→期望断言运行（物理基底裁决）     │
│  ④ L3 边界：额外边界用例（None/空/重复/极端）    │
│  ⑤ 规范符合性：condition_kb 语义对齐 + 结构规范   │
│  ⑥ 集成测试：真实组装 + 回归（域管线全绿）        │
│                                                 │
│  输出：结构化校验报告（pass/fail + 原因 + 证据） │
└─────────────────────────────────────────────────┘
```

## 3. 新增：校验指纹与本地缓存（替代 99.9% 缓存命中）

**关键设计：把"LLM 的缓存命中"替换为"本地校验缓存"。**

```python
# verifier.py 核心数据结构
@dataclass
class VerifyRequest:
    task: str            # 任务描述（排序/循环编译/图遍历…）
    code: str            # 白箱生成的代码
    unit_id: str         # 单元标识（域+序号，如 os_112）
    lang: str = "python" # 语言
    cases: list = field(default_factory=list)   # (输入, 期望)
    deps: list = field(default_factory=list)    # 依赖单元（组装测试用）

@dataclass
class VerifyResult:
    ok: bool
    checks: list         # [("L1语法", True, "证据"), ("L2样例", True, "…"), …]
    fingerprint: str     # 校验指纹（缓存键）
    cached: bool         # 是否命中本地缓存
    reason: str = ""     # 失败原因链
```

**指纹算法**（确定性）：`sha256(task + code + unit_id + lang + cases 序列化 + deps)`
- 相同请求再次到来 → 指纹命中 → 直接返回上次结果（**零计算、零 LLM、零 token**）
- 缓存持久化：`data/verify_cache.json`（主仓库 data/ 目录）

## 4. 校验链（六层，全部确定性）

### 4.1 L1 语法（已有，物理基底）
- `ast.parse(code)` 通过
- 结构规则：函数定义存在、括号平衡、无占位残留、无外部导入依赖

### 4.2 L2 样例（已有，物理基底裁决）
- 每个 `(输入, 期望)` 运行 → 断言相等
- 失败 → 返回实际 vs 期望（可解释）

### 4.3 L3 边界（已有）
- None/空/重复/极端值等边界用例

### 4.4 规范符合性（新增，白箱规则）
- **结构规范**：函数签名（参数/返回）与单元定义一致；命名规则
- **语义对齐**：`ConditionKB.lookup(task)` 查条件路由表 → 代码实现是否命中
  对应规律（如「排序」单元应包含比较-交换结构）
- **协议对齐**：智能论语义（条件空间/名实/信任）映射检查——代码是否
  处理了条件分支、是否声明了类型（名实）、是否含信任语义（C线编译器）

### 4.5 集成测试（已有）
- 依赖单元组装（deps）→ 端到端运行 → 断言
- 回归：域管线全绿（六域 675 单元累积测试）

### 4.6 报告
- 结构化 JSON：每层 pass/fail + 证据 + 失败原因链
- 缓存写入（指纹 → 结果）

## 5. 必须 LLM 的开放判断（目标 <1%）

| 场景 | 判断 | 说明 |
|---|---|---|
| 代码是否符合规范（查表） | **白箱** | 规范=条件路由表/结构规则，确定性查表 |
| 代码能否执行（运行） | **白箱** | 语法+样例+集成，物理基底裁决 |
| 代码意图是否违背协议精神 | ⚠️ 可能 LLM | 开放语义判断，量极小（<1%） |
| 新规律发现（没见过的问题） | ⚠️ 可能 LLM | 探索期，可 Ollama 本地兜底 |

**原则**：能查表的不 LLM，能执行的不 LLM，能规则判断的不 LLM。
LLM 只在「开放语义裁决」保留（如审查代码是否违背智能论核心条款）。

## 6. 实施计划

| 阶段 | 交付 | 验证标准 |
|---|---|---|
| 1（本文档） | 设计 | 设计者审阅通过 |

| 4 | 接入域管线：code_compose 生成 → verifier 校验 → 固化 | 端到端：生成→校验→固化闭环，全程零 LLM |
| 5 | 对照验证：原 LLM 校验环节替换为 verifier | token 消耗归零（缓存命中场景），校验一致率 ≥99% |

## 7. 与 LLM 替代战略的关系

- 本设计是「白箱终裁占比 ≥90%」在代码训练期的落地
- 校验器 = 白箱自举的「验证单元」工程化（预期 vs 实际，物理基底裁决）
- 缓存命中本地化 = 让 99.9% 的重复查询不再产生任何外部成本

## 8. 不做（后续阶段）

- 新规律自动发现（LLM 探索期）——先保证校验闭环零 LLM
- 代码生成质量主观评分（需要人类审美）——只做客观校验
- 分布式校验（单机够用，后续扩展）

## 9. 校准记录（v2/v3，全量对照 681/681 通过）

> 实施计划阶段 2/3 完成后，对六域 681 单元做全量对照审计（外部校准 verifier 规则，
> 使校验器精确匹配真实规范——不放松校验，只消除规则与单元语义的误判）。

### 9.1 v2 修复（首轮审计 604/681 → 校准后 667/681）

| 缺陷 | 根因 | 修复 |
|---|---|---|
| 指纹崩溃（set/lambda/bytes） | `json.dumps` 不支持域单元 cases 的集合推导 `{1,2,3}`/`lambda`/帧解析 `bytes` | `_stable_serialize` 任意类型确定性序列化：set→元素 str 排序、bytes→hex、callable→`__code__` 摘要（co_code+常量+名，跨进程稳定不含内存地址） |
| 指纹崩溃（tuple 键 dict） | 事件委托 cases `{('btn','click'):…}` — dumps 的 default 钩子不处理 dict 键 | 指纹先整体经 `_stable_serialize` 归一化（键 str 化）再 dumps |
| 旧缓存污染新规则 | 规则校准后指纹未变，旧判定被缓存直出 | `VERIFIER_VERSION` 版本失效：缓存文件存版本标记，规则升级 +1 → 旧缓存全部清空重验（= GLM 建议的 protocol_version 落地） |
| `'call'` 注入标记未处理 | L2 把 `'call'` 字符串当输入传函数 | 与 `code_compose.verify_code` 一致：`inp == "call"` 跳过（注入型由集成测试覆盖） |
| L1 括号字符计数误判 | 字符串/注释内括号被字符计数判不平衡（`ast.parse` 已通过即合法） | 删除字符计数检查（AST 层已保证语法合法） |
| import 白名单不全 | `os/struct/asyncio/heapq` 等标准库被当非标准库拒绝 | STDLIB_OK 补全 15 个标准库 |
| structure 规则过粗 | task 含「循环」但字节码/展开实现无 for/while 字面量 | 「循环/递归」移出字面强查（循环语义由 L2 样例裁决） |

### 9.2 v3 修复（667/681 → 681/681）

| 缺陷 | 根因 | 修复 |
|---|---|---|
| 注入型单元误判 | `needs_inject` 单元（图遍历-BFS/编译-类型检查 等）函数依赖注入（Graph/infer_fn），单独跑 L2/L3 必崩 | `expected_structure.inject` → L2/L3 跳过（由集成测试覆盖）；`条件路由图-映射` 补 `needs_inject=True` 标记 |
| dict 期望误判 | VM 执行循环返回完整状态 dict，样例期望只关心 `{'trust':0.8}` | `_assert_match`：dict 期望做子集匹配（got 含 exp 全部键值即可——状态断言语义） |
| 排序结构误判 | 排序键控（`sorted(key=)`）/报文重排序（reorder）无 `<` `>` | 排序 patterns 扩为 `<`/`>`/`sorted`/`key=`/`reorder` |
| 边界类型不符 | 最大团/最大割/生成树计数收 `adj` dict，边界 `[]` 是类型错误；字典反转收 dict 却触发序列反转边界 | ① 单参数名 ∈ 图/状态类黑名单（adj/graph/table/state…）→ 跳过边界生成 ② 边界词表移除「反转」（由样例覆盖）③ 「反转」结构检查排除「字典反转」 |

### 9.3 结论

- **六域 681 单元全量对照通过（681/681，100%）**，缓存 681 条全过（`data/verify_cache.json`）
