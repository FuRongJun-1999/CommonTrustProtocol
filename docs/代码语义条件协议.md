# 代码语义条件协议（Code Semantic Condition Protocol）v1.0

> 状态：文档先行（GPT 2026-08 评审建议 + 荣 CCG 方向确认）
> 定位：**代码实现负责执行，中文语义注释负责声明条件，条件图负责索引，白箱负责路由。**
> 原则：代码不能只有「能运行的实现」，还必须拥有「可被白箱认知和路由的语义入口」。
> 与 CCG 闭合：注释=图的索引（名实），条件图=路由（条件→代码），白箱=执行/路由。
> 哲学映射：功能条件=条件空间（when）、子功能=结构（what parts）、执行方式=过程（how）、
> 不适用条件=盲区边界（when NOT——与盲区注册表同构）。

## 0. 四要素注释格式

每个函数/类/包的语义注释固定为四要素（标记词可兼容既有「生效条件/执行」）：

```python
def predict_routes(problem, context):
    """【功能条件】
    当问题需要根据已有知识寻找可执行推理路径时使用。
    输入必须包含待判断问题与当前认知上下文。

    【子功能】
    ① 识别问题对应条件空间
    ② 沿条件/因果边搜索候选路径
    ③ 条件约束过滤无效路径
    ④ 标记语义诱导路径及可信等级
    ⑤ 无法归属时返回结构性盲区

    【执行方式】
    先识别问题锚点，再沿条件/因果边递归搜索；
    对候选路径做条件约束验证，返回可执行路径及状态。

    【不适用条件】
    ① 输入不存在有效问题锚点时不调用
    ② 不负责修改知识图结构
    ③ 无法验证因果关系时不得将语义相似当作因果结论
    """
```

| 要素 | 标记（兼容） | 含义 | 图索引角色 |
|---|---|---|---|
| 功能条件 | 功能条件 / 生效条件 | 何时使用；输入/前置状态 | 条件节点（路由门槛） |
| 子功能 | 子功能 | 内部能力分解 | 子功能节点（结构检索） |
| 执行方式 | 执行方式 / 执行 | 步骤/调用/结果 | 执行词节点（机制检索） |
| **不适用条件** | **不适用条件**（新增） | 何时不能用；约束/边界 | **盲区节点（负路由）** |

## 1. verifier 检查

- R1 函数/类中文注释（已有）
- R2 注释中文语境（已有）
- R3 三要素标记（功能条件/子功能/执行方式——兼容 生效条件/执行）（已有，681 达标）
- **R4 不适用条件**（新增）：主函数注释须含「不适用条件」标记；
  自动生成草稿（参数边界/None 分支提取）+ 外部精修；升级期软模式，全库达标后开硬检查

## 2. 认知图集成（代码知识入白箱体系）

```
              认知图
                │
     ┌──────────┼──────────┐
     ↓          ↓          ↓
   理论知识    工程知识    代码知识（CCG）
                           │
                      函数/类/包
                           │
                  条件→子功能→执行→不适用
```

白箱遇工程问题「如何实现 X」：
```
问题 → 识别条件 → 查询注释索引（CCG）→ 定位函数/类/包 → 读取实际代码 → 执行/修改
```

## 3. 修改纪律（语义入口约束）

白箱修改代码时，**先改语义声明，再改实现**：
条件描述 → 子功能 → 执行路径 →（不适用条件）→ 实现
——语义与实现同改，索引不失效；CCG 重新建图后检索仍可达。

## 4. 自迭代闭环

```
中文注释 → 语义结构 → 条件图 → 代码定位 → 代码执行
    → 执行结果 → 预测误差 → 更新条件图/注释
```
代码维护纳入白箱自迭代闭环；「何时调用哪段代码」转化为条件识别问题。

## 5. 缺失条件准确率（Missing Condition Accuracy，GPT 实验）

**问题**：DEFER 反推的缺失条件是否=真条件差异（而非描述相似）？
**方法**：GT 用**条件结构**而非自然语言关键词——
`{subject（条件对象）, cond_type（条件类型）, a_side/b_side（两侧判别词）}`。
判定两层：严格（缺失条件同时含 A/B 两侧判别词，同义词归一 门槛≈阈值）；
语义等价（含任一侧判别词）。
**结论**（test_ccg_missing.py，10 对）：语义等价 100%，严格 100%。
- 关键修复：`_semantic_head` 保留冒号前**语义名**（「列表推导式：」→ 列表推导式）。
  旧逻辑 split('：') 把语义名剥掉 → 容器/算法词丢失（列表 vs 字典 无法辨识）。
  head 语义名是任务判别词——「语义密度决定可索引性」在缺失条件层的复现。
- 方向判定优先 task 权威名独有词（干净无碎片）；head 独有词兜底。

## 6. 条件扰动实验（Condition Perturbation，GPT 实验）

**问题**：控制 DEFER→ACCEPT 路由的是【条件】还是【候选语义相似度】？
**方法**：同主体相邻能力对，任务仅互换条件词（累积↔阈值检查、无权↔加权、
列表↔字典），观察路由归属是否按条件预期改变。语义相似度几乎不变——
若路由随条件词改变 → 条件控制路由；不变 → 证伪。
**结论**（test_ccg_perturb.py，3/3 切换 + 混合条件 BLINDSPOT）：
- 条件词扰动 → 路由归属按条件反转（A 条件→A 侧，B 条件→B 侧）。
- 混合条件任务（累积+门槛放行）→ BLINDSPOT 声明，不强行选边（条件冲突不该
  被 DEFER 递归掩盖）。
- 三次迭代修复：
  ① `_diff_condition` 方向对齐任务（否则递归偏航：累积任务 → 阈值检查）；
  ② 递归 query 去掉「（而非 …）」另一侧噪声（防止重新引入）；
  ③ 混合冲突检测需多重证据（两侧都命中且总命中 ≥3，并集去重——
     「导式」=推导式公共后缀不对称碎片 1 个不构成冲突）。

## 7. 路由条件图谱系（GPT 实验链汇总）

```
语义化注释 → 可索引性（盲测 99%）→ 条件化（三要素）→ 正向匹配（96%）
→ 不适用条件（负路由）→ 能力级互斥（对抗 28→88%）
→ 四态路由（ACCEPT/REJECT/DEFER/BLINDSPOT，边界三分类 100%）
→ 缺失条件反推（Missing Condition Accuracy 100%）
→ 条件扰动验证（条件控制路由 3/3，混合条件 BLINDSPOT）
```
白箱特色：拒绝一个「看起来很像」的答案的理由可解释（缺失条件/盲区声明），
黑箱只给「最像」。

## 8. 递归协议化（GPT 第七阶段 §7.1）

**命题**：白箱能在条件不足时递归找到决定性条件，并把得到的规则可靠地转化为
可验证执行。递归不是「继续搜索」——**每一轮都必须让条件空间变小**。

### 8.1 状态机与转移（四保护）

```
START → 条件提取
  ├─ 条件充分且唯一 → ACCEPT
  ├─ 条件与能力冲突 → REJECT
  ├─ 条件不足但存在可寻找条件 → DEFER → 生成 missing_condition
  │     → 搜索条件 → 条件补全 → 重新路由
  ├─ 无法形成可靠条件判断 → BLINDSPOT
  └─ 两侧条件冲突 → BLINDSPOT
```

四个保护（防 DEFER 无限递归/循环/无效递归）：
1. **递归深度上限**：默认 `max_depth = 3`，复杂任务显式申请扩展。
2. **条件循环检测**：递归要求已搜索过的缺失条件（seen_missing 命中）→
   立即 `DEFER_EXHAUSTED`（递归不收敛声明，等价 BLINDSPOT 且带 exhausted 标记）。
3. **信息增益门槛**：新条件必须减少候选集（candidate_after < candidate_before）
   或提高路由确定性，否则终止递归（gain ≤ 0 → DEFER_EXHAUSTED）。
4. **递归预算**：限制递归轮数（= max_depth）+ 每轮候选数（top）。

### 8.2 结构化状态（RouteState）

```json
{
  "state": "DEFER",
  "depth": 1,
  "missing_condition": {
    "subject": "信任值", "cond_type": "累积 vs 阈值检查",
    "a_side": ["累积"], "b_side": ["门槛", "阈值", "放行"]
  },
  "candidate_count_before": 2,
  "candidate_count_after": 1,
  "information_gain": 0.5,
  "next_query": "信任值是否需要累积，还是只需判断是否达到门槛"
}
```

MissingCondition 由 `_diff_condition` 输出字符串升级为结构化对象
（subject/cond_type/a_side/b_side——与 Missing Condition Accuracy 的
条件结构 GT 同构，见 §5）。

### 8.3 递归指标（test_ccg_recursive.py → recursive_trace.json）

- **Recursive Direction Accuracy**：递归查询命中真实条件方向的样本数 /
  所有需要递归的样本数（GPT §三.2）。
- 递归收敛率（DEFER→ACCEPT 比例）/ DEFER→BLINDSPOT 比例 / 循环率
  （DEFER_EXHAUSTED 比例）/ 平均深度 / 最大深度 / 无效递归率
  （信息增益 ≤0 比例）。

### 8.4 精准执行闭环（GPT §五，7.2 起）

```
问题 → 条件识别 → 路由 → 规则匹配 → 生成执行计划 → Dry-run
→ 检查前置条件 → 真实执行 → 结果验证 → 记录与固化
```
「我找到了一个看起来相关的代码单元」≠「我有资格执行这个代码单元」——
执行前必须输出 selected_capability / conditions / rule / expected_result /
verification / rollback。
