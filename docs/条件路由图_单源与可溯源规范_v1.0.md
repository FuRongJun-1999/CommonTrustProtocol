## 一、单源声明表（Single Source Table）

任何资产有且只有一个真源路径。**修改只能发生在真源**；别处出现的同名文件一律视为待归档副本。

| 资产类别 | 唯一真源 | 禁止位置 |
|---|---|---|
| 灵枢核心包（aeis.*） | `aeis/aeis/*.py` | 仓库根 / aeis/ 顶层散件 |
| 白箱智慧模块（wisdom 包，随 wheel 发布） | `aeis/wisdom/*.py` | tools/、根 wisdom/、aeis/wisdom/tools/ |

| 历史版本 / 废弃草稿 | `docs/history/` · `historical/scripts|duplicate_snapshot/` | （冻结只读，永不回迁主线） |

## 二、变更路由四则

1. **改前查表**：动手前先在本表定位真源。在镜像上修改 = 无效劳动 + 制造分叉，视同违反红线。
2. **修改走八步闭环**（沿用主仓库修改纪律 v1.0 §2.2）：感知→识别→分析→验证→固化→记录→反馈→方向性自检；其中「分析」必须列出影响面，「反馈」必须声明是否产生新副本（答案应为否）。
3. **路径注入禁令**：`sys.path.insert(0, r'D:\...')` 式绝对路径一律禁止。模块定位用 `os.path.dirname(os.path.abspath(__file__))` 相对解析；跨包导入走正常包机制（如 `wisdom.verifier`）。（本轮已消除 6 处：4 测试 + AEIS_COPY + DEFAULT_DB）
4. **归档而非删除**：被收敛/废弃的副本 git mv 进 historical/（保 git 历史），并在同名报告中登记判定依据；确证无独有内容的纯拷贝可直接归档，双向分叉文件必须先合并再归档。

## 三、可溯源证据链

每笔提交必须可回答四个问题（证据写在提交信息或关联报告节）：

| 问题 | 证据形式 |
|---|---|
| 为什么改 | 关联 issue/报告章节/荣指令原文（日期+出处） |
| 影响什么 | 影响面清单（哪些模块/副本/发布物受波及） |
| 怎么证明没破坏 | 金标准输出原文（六域管线/编译器/P线/生态组装 的通过行） |
| 真源在哪 | 本表的资产行号或路径 |

**数字口径纪律**：README/文档中出现的每个统计数字（单元数/工具数/通过率）必须在同仓可复现——不可复现的数字删除或标注「历史值」。当前锁定基线：六域管线 **1058 case**、编译器 **272**、P 线 **240**、图数据库 **123**、固化库 **619**、MCP 工具 **73**。

## 四·五、写卡纪律 · 规范型优先（T8/T9 实证反哺 · 2026-08-28）

来源：T8 token 对照（题级 5.1 倍）与 T9 项目级对照（6 领域）实验证据。

1. **卡的「执行」字段必须是规范型**：精确行为规范（怎么做/边界 case/
   返回结构），不是描述型（是什么/类比）。实证：类比文字（如「像整理
   手牌」）注入 LLM 实现任务时会干扰实现方向（T9 排序项目 A 组 5 轮
   失败主因之一）；规范型卡使 A 组首轮通过（T9 字符串项目 2 轮 vs B 5 轮）。
2. **按用途分卡型**：规范型卡服务实现任务（代码生成/操作规程），
   描述型卡服务知识问答（概念解释）——写卡前先判断注入后的用途。
3. **数值与边界必须显式**：可执行数值（如「预算=月收入×0.3」）与
   边界 case（空输入/零/重复）写进执行字段——它们是「必然事实」，
   LLM 自己想不可靠（外部实验与 T9 双败项目双证）。
4. **直答文案兼顾判定口径**：直答会作为白箱返回值，措辞应覆盖该卡
   领域的关键事实词（缓解自动判定的压缩表达伪影）。
