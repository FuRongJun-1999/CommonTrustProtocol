## 二、排查路径复盘（哪些快、哪些慢）

**快的**：
- GAP_DEBUG 环境开关取证点（gap 判定现场落盘 r 全量+env 快照）——**一次取证终结五轮假设**：现场显示「✔ 缓存命中」直接把问题从「执行错误」重定义为「缓存投毒」。
- 最小实验（直接 exec pattern + fn(*inp)）证明 L2 本身全绿——把嫌疑从代码收窄到环境/缓存。

**慢的（教训）**：
1. **修复后立即验证被缓存屏蔽**——16:56 完成 tuple 修复，17:0x 验证「清缓存后 True」看似通过，实则每次清除都被并发写回抵消，连续三轮误判「已修复但循环未重启」。
2. **写方清单不完整**——五轮排查只盯着「循环进程+交互实验进程」两个显性对手，第六轮用 PowerShell 清点全部 python 进程才发现第三个写方（长驻 MCP server）。**修并发问题前必须枚举所有持句柄的进程**。
3. **进程管理工具反复失败浪费轮次**——wmic 输出行尾 \r 导致 PID 提取多次失败（「无效查询」），taskkill 从未真正杀掉目标进程；换 PowerShell Get-CimInstance/tasklist 一次成功。Windows 下优先 PowerShell。

## 四、可复用的方法论沉淀

1. **非确定性问题三步法**：①部署现场取证点（环境开关控制落盘）→ ②对比两环境的取证差异 → ③差异点即根因方向。不要在取证前堆假设。
2. **缓存类诡异第一个检查点 = 「缓存命中」标记**——判定结果来自缓存还是真实执行，决定后续完全不同的排查方向。
3. **修复的验证必须考虑缓存屏蔽**——改了数据/代码后，先确认验证路径真的走了新逻辑（冷执行），再下结论。
4. **长驻进程是「文件修复」的天然敌人**——它内存里的旧快照会把磁盘上的修复写回。清文件必须伴随重启所有写方进程，或版本化缓存（bump 即全局作废）。
5. **审计工具自身的口径也是嫌疑源**（本案例前奏：L2 扫描器闭包误报同型问题）——验证器口径三源教训的又一次应验。
