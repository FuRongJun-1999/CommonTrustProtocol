## 四层语义（验证什么）

- **L1 条件化知识**：工程的知识资产以 KCCS 条件卡/白箱单元形态存在（非散文档）
- **L2 确定性路由**：触发词查询 → 卡/单元命中，0 LLM token，分数阈值可判定
- **L3 物理基底裁决**：真实执行（编译/VM 运行/单元管线），结果不由系统自评
- **L4 编辑器可达**：条件路由图统一入口（KCCS LSP hover 同源查询）——知识进入写代码的工作流

## 验证过程抓到的问题（方法论价值）

1. **模块名冲突**：`aeis.core`（顶层 core）与 protocol-compiler 的 `core` 包
   撞名——常规 import 解析到错误模块。修法：清 sys.modules 缓存 + PC 根
   路径插最前。**对 LSP/编辑器集成是真实风险**（同进程多包场景）。
2. **两套 compile_source 口径**：wisdom.core.compiler（返回元组，compile_exec
   同源）vs protocol-compiler core.api（返回 CompileResult 对象）——
   验证统一走 wisdom 通道（与 MCP 工具一致）。
3. 首版脚本自身的 card_route 未导入/L3 查询词不精确——**验证器也要先自验收**（T9 教训复现有效）。
