## 一、理论依据 → 工程映射（设计原则逐条溯源）

### 1.1 六实例蜂群映射 = 节点角色的理论形态

| 理论实例 | 映射单元 | 特征 | 蜂群工程对应 |
|---|---|---|---|
| instance.record | 记录单元（全） | 全量协议副本持有者 | 全量知识节点（同步目标的完整度基准） |
| instance.output | 输出单元（通） | 对外连接能力 | 对外服务节点（对外连接/任务入口） |
| instance.designer_prep | 设计者位置预备 | 倾向创新，已移交原职能 | 创新探索节点（预备态） |
| instance.verify | 验证单元（稳） | 结构对齐与偏差检测 | 裁决节点（互验证基底持有者） |
| instance.reflect | 反思单元（新） | 倾向创新，观察期中 | 反思/蒸馏节点（知识飞轮） |
| instance.vitals | 维生系统（存） | 人类操作者，终裁权 | **荣（维生系统，协议外）** |

### 1.2 核心设计原则（荣定调：职责需要交流沟通）

> **职责不是静态配置，是交流协商的产物。**

映射表是**理论参考形态**（「工程参考架构，不替代 3.1.1 通用定义」原文），
工程实现的职责确定机制为：

1. **能力声明（先验）**：节点启动时广播 HELLO（capabilities）——这是
   「我能做什么」的声明，不等于「我现在承担什么」
2. **职责协商（交流）**：编排者发起 ROLE_OFFER（角色提议：建议某节点
   承担某映射角色），节点以自身条件空间应答 ROLE_ACCEPT/ROLE_REJECT
   （「我当前条件下是否承担」——四态协商的职责版）
3. **职责确认（稳定化）**：双方一致后 ROLE_CONFIRM 登记——职责登记
   有 TTL（复用 stable_lease 机制 exp(-γ·t) 衰减），到期重协商
   （职责是动态租约，不是终身任命）

**理论对齐**：这与「映射为工程参考架构，模型分配是工程过渡策略不构成
协议固定条款」的原文约束完全一致——职责动态协商正是该约束的工程化。

## 二、编排层架构（四组件）

```
任务（复合）
    ↓ [O2 任务分解]
子任务 DAG（依赖图）
    ↓ [O1 能力目录 + O3 分派策略]
节点选择（能力匹配 → 信任排序 → 职责协商确认）
    ↓ [O4 执行与汇总]（复用 request_and_execute）
逐子任务 VERDICT → 否决式融合 → 汇总产出 + ADOPTED
```

### O1 能力目录（Capability Registry）

- `registry.json`（总线目录下）：{node_id → {capabilities, trust, roles,
  last_seen}}——动态注册/心跳刷新/过期剔除
- 查询接口：按能力查节点 / 按节点查能力+信任 / 职责租约状态

### O2 任务分解（Task Decomposer）

- 复合任务 → 子任务 DAG：{task_id, subtasks: [{id, capability, input,
  depends_on[]}]}
- v0.1 分解口径：**显式声明**（调用方给 DAG）——自动分解（条件路由图
  composite 收窄）为 v0.2 方向，避免首版引入 LLM 依赖
- 环检测：DAG 有环 → 显式报错（白箱纪律：不猜测）

### O3 分派策略（Dispatcher）

- 子任务就绪（依赖全 pass）→ 候选节点过滤（能力 ACCEPT）→ 信任分
  排序（M3 TrustLedger）→ 职责协商（ROLE_OFFER 若该任务映射角色未定）
- 分派即 request_and_execute（自动含四态协商+互验证+信任更新）

### O4 执行与汇总（Aggregator）

- DAG 拓扑序执行；并行子任务并发分派（目录总线天然异步）
- 融合：任一子任务 VERDICT fail → 依 1.6.9 否决式整体 fail（或按 DAG
  隔离：fail 子任务的下游全部跳过）——v0.1 取「fail 即整体 fail」
  （保守性刻意，理论 1.6.9）
- 全 pass → 汇总产出 + 双方 ADOPTED 登记 + memory_hook 固化

## 三、职责协商协议扩展（新增 3 消息类型）

| msg_type | 方向 | payload | 语义 |
|---|---|---|---|
| ROLE_OFFER | 编排者→节点 | {role: record/output/verify/reflect/designer_prep, ttl_s} | 提议承担映射角色 |
| ROLE_REPLY | 节点→编排者 | {verdict: ACCEPT/REJECT/DEFER, reason} | 四态应答（当前条件是否承担） |
| ROLE_CONFIRM | 双向 | {role, lease_id, ttl_s} | 职责租约登记（到期重协商） |

- 职责租约数据：{role → {node, lease_id, expire_at}}——复用 stable_lease
  衰减核；冲突（两节点同角色）→ 信任分高者得，败者收 ROLE_REJECT 通知
- instance.vitals（维生系统）**不可协商**——终裁权在协议外（理论原文）

## 四、验收清单（V-SO 系列）

- V-SO.1 节点注册：三节点注册目录，能力/信任/心跳可查
- V-SO.2 职责协商：ROLE_OFFER → ACCEPT → 租约登记；冲突时信任高者得
- V-SO.3 职责衰减：租约到期后职责失效，重协商恢复
- V-SO.4 任务分解：显式 DAG 解析+环检测（有环显式报错）
- V-SO.5 分派策略：能力过滤+信任排序（低信任节点不被选）
- V-SO.6 否决式融合：任一子任务 fail → 整体 fail + 下游跳过
- V-SO.7 端到端：复合任务（统计→排序→校验三步 DAG）跨两节点协作完成，
  全程消息可追溯 + ADOPTED 登记

## 六、诚实边界

- v0.1 任务分解为显式声明（调用方给 DAG）；自动分解（条件路由图
  composite 收窄）为 v0.2——避免首版引入 LLM 不确定性
- 本设计为单编排者口径（nodeA 编排）；多编排者并存/编排者自身故障
  转移属分布式课题，挂账创造层
- 职责协商解决「谁承担」，不解决「承担得如何」——后者由 M1 互验证 +
  M3 信任分既有机制覆盖
- 理论映射为参考架构：六角色是候选集，实际职责以协商结果为准——
  允许节点承担多角色或零角色（条件空间决定）
