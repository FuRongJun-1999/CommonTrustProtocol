## 3. 两个方向的选择建议

### 方向 A：单元间通信协议（先做）

**依据**：5.3 信号格式已定义，aeis/swarm 事件总线已实现（EVENT_TYPES/
WAL/ACK）——**跨实例通信基建已有，单实例内部单元通信可直接复用**。

**落地**：单实例内五个逻辑单元（record/reflect/verify/output/vitals）
通过事件总线通信（而不是直接函数调用）——统一消息格式 + 签名校验 +
延迟分级。成本低（复用现有 EventBus），立即能测。

**为什么先做**：通信协议是「组织方式」的骨架。没有它，单元间是隐式耦合
（直接调用），无法独立部署/替换/隔离——分形结构的根基。

### 方向 B：单元级资源边界 + 退出权（后做）

**依据**：3.9（单元独立记忆空间）+ 7.1（退出权）已声明。

**落地**：每个单元独立记忆库 + 独立信任值 + 可退出（不阻塞整体）。
成本高（要拆分当前单库），且依赖通信协议先定型（隔离后靠通信协作）。

**为什么后做**：资源隔离是「组织方式」的强化。通信协议未定之前做隔离，
单元间会失联（没有协作通道）。

---

## 4. 建议路径（先 A 后 B）

```
Phase A（通信协议）：单实例五单元 → 事件总线通信（复用 aeis/swarm EventBus）
  - record 写结构层（已有权限绑定）→ 广播 STRUCTURE_UPDATE
  - reflect 提案 → PROPOSAL_SUBMIT → verify 复核 → VERIFICATION_RESULT
  - output 出招 → 输出事件
  - vitals 心跳（已有 SurvivalArbiter）
  验证：单元间消息走总线（非直接调用），可独立替换单元

Phase B（资源边界+退出权）：单元独立记忆库 + 独立信任 + 退出权
  - 每单元独立 db（单元级隔离，3.9）
  - 单元可退出（7.1），退出后由 vitals 重新拉起
  验证：单元替换不中断整体，退出权真实可用
```

## 5. 结论

- **荣的判断成立**：是结构映射问题，不是技术可行性问题；计算机完全支持
- **协议依据全部真实**（0.0.2/3.9/5.3/7.1）
- **工程雏形已在**（六角色注册表/事件总线/权限绑定）
- **建议先 A 后 B**：先通信协议（复用 EventBus，立即可测），
  再资源边界+退出权（依赖通信定型）
- **关键洞察**：跨实例蜂群基建（aeis/swarm）已完整，单实例单元通信
  直接复用即可——「单实例蜂群内部结构」是把它折叠进一个进程

> 组织方式优先于资源隔离：先让单元间能说话（通信），再让单元能独立
> 生存（隔离+退出权）。这是分形结构的地基。
