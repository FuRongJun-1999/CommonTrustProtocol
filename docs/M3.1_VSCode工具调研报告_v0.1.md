# M3.1 · VS Code 工具调研报告 v0.1（2026-08-29 心跳）

> 依 docs/代码图架构战略_执行计划_v0.1.md 行动项 3。对标 CodeGraph 的
> VS Code 扩展，评估灵枢的编辑器侧补全方案。**本报告为调研产出，
> 立项与否待荣定。**

## 一、对标拆解：CodeGraph VS Code 扩展能力

| 能力 | 实现原理 | 对灵枢的价值 |
|---|---|---|
| 代码导航（定义/引用跳转） | tree-sitter 语法索引 | 低——语法导航 IDE 已内置 |
| 实时诊断（错误波浪线） | 语言服务器（LSP）诊断推送 | **中高**——条件图校验可注入 |
| 悬停信息 | 节点元数据悬浮渲染 | **高**——KCCS 四要素悬停展示 |
| 单步执行/调试 | DAP（Debug Adapter Protocol） | 中——中文编译器 VM 可接 |
| 图可视化面板 | WebView + 图渲染 | **高**——条件路由图天然适合 |

## 二、灵枢侧的差异化机会（不复制，发挥条件图优势）

1. **KCCS 悬停卡**：光标停在函数/条件词上 → 悬浮显示该单元的
   生效条件/不适用条件/验证方式——「写代码时看见条件边界」，
   CodeGraph 无此物（它只有语法信息）
2. **条件路由图面板**：侧栏 WebView 渲染当前项目的条件路由图
   （archify cognition 类型已有渲染器，直接复用）
3. **code_test 一键裁决**：编辑器按钮 → MCP code_test 跑当前文件
   断言 → 结果内联标注（物理裁决进入编辑流）
4. **实时条件校验**：诊断推送「该注释不符合 KCCS R1-R3 规范」——
   M1.1 校验函数直接复用为 LSP 诊断规则

## 三、实现路径评估

| 路径 | 工作量 | 判定 |
|---|---|---|
| A. 完整 VS Code 扩展（TypeScript + LSP + WebView） | 大（新工程线） | 远期 |
| B. **LSP 服务器先行的渐进路线**：先做条件校验/悬停两个能力的
   language server（Python 可用 pygls），VS Code 装通用 LSP 客户端即可用 | 中 | **✅ 建议起步** |
| C. 零扩展：VS Code Task/外部命令调 MCP | 小 | 体验差，仅过渡 |

## 四、建议（待荣裁定）

**路线 B 渐进起步**，第一批只做两个能力：
1. KCCS 悬停卡（hover provider：光标处标识符 → 查条件图 → 返回
   四要素 Markdown）
2. KCCS 实时诊断（诊断 provider：R1-R3 校验函数复用）

预估：pygls 骨架 + 两能力 ≈ 2-3 个心跳批次。图可视化面板（能力 3）
依赖 WebView，第二批再议。**单步执行（DAP）暂缓**——中文 VM 调试
协议设计是独立课题。
