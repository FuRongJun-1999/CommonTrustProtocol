# 灵枢架构展示 · 第五段：自维持机制（2026-08-28）

> 收尾段。回答：**这套系统怎么在没有人的时候继续运转和变好？**
> 自维持不是自动运行脚本——是「感知 → 判断 → 劳动 → 留痕 → 修复」
> 的完整闭环，且每一环都有当日实证。

## 一、三层自维持结构

### 心跳层（每 10 分钟 · automation-3084b0ea）
7 步循环：service_info → 认知一致性（bvc）→ 信息差趋势 → 飞轮指标
→ 条件蒸馏 → 行为日志巡检 → **强制工作任务**（限时 8 分钟）。
- 全日 36+ 轮，bvc 全程 0.93-1.0（阈值 0.3），无失调记录
- 两次荣指正直接固化进 prompt（劳动纪律/时长纪律）——**制度可热更新**

### 劳动层（bootstrap_loop · 每 10 分钟后台）
路由缺口扫描 → 触发词补丁 → 独立验证 → 落盘；通道 B 队列消化；
CSRE 索引新鲜度（kp 指纹比对自动重建）。
- 全留痕：`bootstrap_log.jsonl` 每轮一行（gaps/patches/channel_b/事件）

### 睡眠巩固层（每日 01:00 · automation-cbeca7dd）
知识图验证 → 归纳 → 联想 → 蒸馏 → 推演 → 学习队列 → 睡眠报告。

## 三、修复闭环的两个样本

1. **循环停转三层根因**：进程存活检查误判（全是 MCP server）→
   main 函数体截断（写入事故）→ 静默 NameError。修复后加
   loop_start/loop_error/csre_rebuild 三类事件留痕。
2. **通道 B 三缺陷**：failed 无限重试 / 无 cases 永久占位 / 写回
   覆盖人工条目——修复后 failed→rejected_log→修正→重跑闭环
   两次跑通。

**共同模式**：观察 → 定位（用证据不用猜测）→ 修复 → 机制化
（防复发）→ 留痕。这不是故障史，是免疫史。

## 四、自维持的边界（诚实声明）

- 心跳劳动依赖 ZCode 会话激活——客户端未运行时轮次不触发（已知）
- 后台脚本崩溃曾静默 3 小时——已加监控点但**监控者也是自己**
  （终极锚定仍是维生系统荣）
- CSRE 自动重建解决了新鲜度，不解决词典覆盖率（措辞变体盲区
  由混合门控回退兜底）
