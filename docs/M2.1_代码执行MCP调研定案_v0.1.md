## 一、现状盘点（调研结论的根基）

1. **MCP server 已有命令执行工具**（aeis/aeis/mcp/server.py:330）：
   `subprocess.run` 参数列表形态（禁 shell 字符串/管道/重定向——防注入），
   返回 {status, exit_code, stdout, stderr, elapsed_s}。**「运行任意命令」
   已覆盖**——Python 片段可经 `python -c` 执行。
2. **缺口**：无**结构化代码测试**工具——「跑一段代码+断言集，逐条返回
   结果」是白箱验收的高频动作（T9/T10/V-P 全部手工写 runner），值得工具化。
3. Docker 28.4.0 已安装但 **daemon 不可用**（容器沙箱方案当前不可运行）。

## 二、方案对比

| 方案 | 隔离 | 依赖 | 判定 |
|---|---|---|---|
| A. 现有 exec + 新增 code_test 专用工具（临时目录+timeout+逐条断言） | 本机信任域 | 零新依赖 | **✅ 定案** |
| B. Docker 容器沙箱 | 强 | daemon 不可用 | 可选强化（后续） |
| C. RestrictedPython/ast 白名单 | 强（Python 限定） | 新依赖+功能受限 | 否——物理裁决要跑真实代码 |

## 三、定案（方案 A'）

**新增 `code_test` MCP 工具**（复用现有 exec 的防注入设计）：
- 输入：`{code, tests[], timeout_s?=10}`
- 执行：临时目录 + `python -I`（隔离模式：忽略环境变量/用户站点）+
  subprocess timeout
- 返回：`{passed, results: [{test, ok, error}], stdout}` ——逐条断言结果
- 与现有 exec 的分工：exec=通用命令（已覆盖运行）；code_test=结构化
  验收（白箱高频动作工具化）

**安全边界显式（诚实声明）**：
- 信任域=本机 agent 工作流（与现有 exec 同信任域，非对外服务）
- 约束：timeout（默认 10s）、临时目录隔离、`-I` 隔离模式、无 shell
- 不防：恶意代码对本机的直接损害（同信任域内不设防——边界外扩需
  Docker 沙箱，属可选强化）
