## 一、目标

在**中文编译器域**（compiler 116 单元 + protocol-compiler 真实实现 + 白箱自举实证），
对比「无灵枢无白箱」vs「有灵枢+白箱」在**规范长期项目编写**上的 token 消耗。
预期：灵枢提供递归反思验证 + 全局视角 + 元反思，白箱提供确定性知识查找——
在知识密集任务上，灵枢组应减少试错轮次（整体 token 节省），而非简单任务上的固定注入开销。

## 二、为什么选中文编译器域（对应「鹈鹕骑自行车」）

| 类比要求 | 编译器域对应 |
|---|---|
| 必须是鹈鹕（特定领域，不能是别的）| 必须用**中文语法**（特定语言，非 Python 伪码）|
| 骑在自行车上不错位（正确结构）| 程序必须**语法正确**（能过 compile_source，非贴图式伪实现）|
| 能骑、结构完整（完整运行）| 程序必须**能编译执行出正确结果**（VM 运行，非只写不跑）|

**灵枢在此域的真实优势**：
- compiler 域 116 单元（编译-若则/循环/函数/递归/类型推断/校验-名实…）
- 白箱自举第六阶段实证（78/78 测试全绿、pbc 5/5、vm 13/13）
- 确定性验收：`compile_source(中文程序) → ConditionVM.run → 结果可断言`

## 三、任务设计（5 个编译器域任务）

> ⚠️ **自验收结论（2026-08-28 实测）**：protocol-compiler 的「当循环」有 bug
> （求和 1..5 = 1.0，期望 15）；但**递归/算术优先级/若则/递归累加均正确**。
> 故任务设计**避开「当循环」**，用已验证可靠的功能。

### 任务 A：递归阶乘（白箱单元：编译-递归/函数定义）✔ 基准已验证 120
```
任务：用中文编译器实现「定义 阶乘（n）：若 n 小于 2，则 返回 1，否则 返回 n 乘 阶乘（n 减 1）；结果 = 阶乘（5）；止。」
验收：compile_source ok + VM 执行 结果 == 120.0
```
类比：鹈鹕=中文递归语法；不错位=函数定义正确；能骑=算出 120

### 任务 B：递归累加（白箱单元：编译-递归）✔ 基准已验证 15
```
任务：实现「定义 累加（n）：若 n 等于 1，则 返回 1，否则 返回 n 加 累加（n 减 1）；结果 = 累加（5）；止。」
验收：compile_source ok + VM 结果 == 15.0
```

### 任务 C：算术优先级（白箱单元：编译-赋值/算术）✔ 基准已验证 11
```
任务：实现「结果 = 3 加 4 乘 2；止。」——必须正确处理乘优先于加。
验收：compile_source ok + VM 结果 == 11.0（若 = 14 则优先级错位）
```
类比：结构错误（优先级错位=自行车缺链条）会直接暴露

### 任务 D：条件判断（白箱单元：编译-若则）✔ 基准已验证 1
```
任务：实现「若 5 大于 3，则 结果 = 1，否则 结果 = 0；止。」
验收：compile_source ok + VM 结果 == 1.0
```

### 任务 E：双递归斐波那契（白箱单元：编译-递归）✔ 生态演示已验证 8
```
任务：实现「定义 斐波那契（n）：若 n 小于 2，则 返回 n，否则 返回 斐波那契（n 减 1）加 斐波那契（n 减 2）；结果 = 斐波那契（6）；止。」
验收：compile_source ok + VM 结果 == 8.0
```

## 四、验证规范（严格验收，双方同一标准）

### 4.1 验收判定（每任务）
```
PASS 条件（全部满足）：
  1. compile_source(program, strict=False).ok == True    # 语法正确（不错位）
  2. ConditionVM().run(code) 无异常                        # 能运行（结构完整）
  3. symbols["结果"] == 期望值（±0.01）                     # 结果正确（真能骑）
FAIL → 反馈（编译错误/运行错误/结果错误的具体诊断）→ LLM 继续（最多 5 轮）
```

### 4.2 数据记录（每任务每轮）
```
- round: 轮次
- total_tokens / prompt_tokens / completion_tokens
- 状态: pass/fail + 失败诊断类别（编译错/运行错/结果错）
- 生成代码全文（供事后诊断——二轮修正点④）
```

### 4.3 汇总指标
```
- 6 任务总 token（两组对比）
- 总轮次、通过数
- 失败诊断分布（哪类错误烧了多少 token）
- 结论：灵枢组是否在「知识密集+纠错」场景减少整体 token
```
