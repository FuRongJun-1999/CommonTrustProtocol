# 功能格类型库（ls20 游戏 · 网页端知识性内容）

> 来源：zcode 测试确认的 ls20 真实机制（4 方向移动 + 功能格 + 状态匹配目标）
> 状态：基于已实测确认的类型（v1）；扩展类型标注「待实测确认」——诚实校准，不虚构未验证机制

## 一、基础机制（ls20 实测确认）

| 机制 | 说明 |
|---|---|
| 移动 | 玩家/物体 4 方向移动（上下左右） |
| 功能格 | 特殊格子，物体接触/踩入后触发特定效果 |
| 目标匹配 | 物体状态（颜色/形状）与目标匹配即通关 |
| 状态 | 物体携带属性（颜色/形状/位置），可被功能格改变 |

## 二、功能格类型（已实测确认）

### 1. 旋转格（rotate）
- **行为**：物体进入后旋转 90°
- **适用条件**：物体形状需要转向（如横向→纵向）
- **策略**：识别目标所需朝向 → 规划经过旋转格的路径
- **观测**：旋转改变物体朝向，不改变颜色/形状类别

### 2. 换色格（recolor）
- **行为**：改变物体的颜色
- **适用条件**：物体颜色与目标不匹配
- **策略**：颜色是状态匹配的维度之一 → 需经过对应换色格使颜色对齐目标
- **观测**：换色只改变颜色属性

### 3. 换形格（reshape）
- **行为**：改变物体的形状
- **适用条件**：物体形状与目标不匹配
- **策略**：形状匹配目标 → 规划经过换形格的路径
- **观测**：换形只改变形状属性

### 4. 目标格 / 状态匹配格（goal / state match）
- **行为**：物体状态（颜色+形状）与目标一致时，判定通关/完成
- **适用条件**：所有状态维度（颜色/形状/朝向/位置）匹配
- **策略**：先规划状态变换（旋转/换色/换形），再到达目标格
- **观测**：状态匹配是最终判定的条件

## 三、功能格交互模式（已确认的规律）

- **状态变换链**：物体状态 = f(经过的功能格序列) → 目标匹配需要设计经过哪些功能格
- **条件识别**：每关的目标（颜色/形状/朝向）决定需要哪些功能格、以什么顺序经过
- **自迭代**：试错 → 观测状态变化 → 修正功能格路径 → 目标匹配

## 四、待实测确认（扩展候选，不建库）

| 候选类型 | 猜测行为 | 状态 |
|---|---|---|
| 传送格 | 物体传送到另一位置 | 待确认 |
| 破坏格 | 摧毁物体 | 待确认 |
| 冻结格 | 锁定物体状态 | 待确认 |
| 加速/减速格 | 改变移动步数 | 待确认 |

> 确认一种补一种（条件路由表增量扩展），不虚构。
