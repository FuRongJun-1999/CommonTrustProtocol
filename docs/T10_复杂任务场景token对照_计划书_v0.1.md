# T10 · 复杂任务场景 token 对照 · 项目计划书（v0.1 · 2026-08-28）

> 发起：心跳自主立项（依据 T9-2 收官结论：灵枢价值验证场景=复杂任务/
> 知识密集/长会话——简单任务场景已被 T9-2 双端交叉验证排除）
> 执行：zcode（GLM 端）；待 deepseek 端交叉验证

## 一、假设

T9/T9-2 证明：任务一次可过 → 灵枢机制注入是纯固定开销。
T10 反向设计：**任务本身复杂**（多组件交互/规则密集/边界丰富）——
模型一次写对在任务属性上就不可能，纠错轮次是任务固有属性而非断言缺陷。
在此地基上对比：灵枢全管线（递归反思+声明注入+规范卡+软注入门控）
能否通过「减少纠错轮次/提高首过后的收敛速度」实现总 token 反超。

## 二、场景设计原则（区别于 T9 的简单任务）

1. **多组件交互**：单函数 → 多函数协作（状态依赖/数据流转）
2. **规则密集**：领域规则 ≥5 条且互相作用（非单一公式）
3. **边界丰富**：≥6 个边界 case（自然存在，非断言强加）
4. **验收确定性**：仍是可执行断言（白箱裁决）
5. **诚实控制**：任务描述完整自洽（一轮 T9 的断言歧义教训）——
   复杂度来自任务本身，不来自描述缺陷

## 三、项目集（4 个复杂项目 · 草案）

### P1 订单状态机（规则密集）
状态：待支付→已支付→已发货→已完成 + 取消分支（仅待支付可取消）。
实现 advance(state, action) → 新状态；非法流转抛 ValueError（含当前态
与 action）。≥10 断言（合法流转 ×5 + 非法 ×5）。
白箱卡：无现成卡——**预置规范型卡**（状态流转表）。

### P2 日历推算（规则密集）
实现 next_weekday(y, m, d) → 下一个工作日（跳过周末；闰年/跨月/跨年）。
≥8 断言（平年/闰年 2 月/年末跨年/周五→周一）。
白箱卡：预置闰年规则卡（能被 4 整除不被 100 整除，或被 400 整除）。

### P3 账单聚合（多组件）
实现 summarize(records) → {"total", "by_category", "top"}：
过滤 amount>0 → 按类目聚合 → 总额保留两位 → top 类目。
≥8 断言（空输入/负数过滤/并列 top/精度）。
白箱卡：预置聚合规范卡。

### P4 编译器组合程序（接 T9-2 地基）
中文编译器实现：定义 面积（r）：…（圆周率取 3.14）+ 定义 总面积（rs）：
递归求和多个圆面积；结果 = 总面积（…）。多函数+递归+算术组合。
白箱卡：T9-2 已有编译单元语义要点。

## 四、管线（A 组灵枢全管线 v2）

1. 递归反思分析（1 次 LLM，计入成本）
2. 白箱查找：声明注入（T9_INJECT_MODE=declaration）+ 规范型卡内容
   （预置卡为规范型——层级对齐，不触发诱导）
3. 实现 → 严格验收 → failing 结构化反馈 → 循环 ≤8 轮（深迭代）
4. 每轮记录：token/断言结果/代码全文

B 组：同任务同验收，裸提示词（任务+语法/接口说明），同循环。

## 五、度量与判定

- 主指标：**通过率**（T9 二轮 A 4/6 vs B 3/6 的差距是否在复杂场景放大）
- 次指标：总 token、首过率、平均收敛轮次
- 判定：A 组通过率优势 ≥2 项目且总 token 差距收窄至 30% 内 →
  「复杂场景机制税被通过率覆盖」成立；否则诚实记录机制税在复杂场景
  同样不可覆盖

## 六、执行顺序

1. ⏳ 预置规范型卡 ×3（状态机/闰年/聚合——写卡按四·五节纪律）
2. ⏳ runner（复用 token_ab_project_bench 框架，MAX_ATTEMPTS=8，
   注入=declaration+规范卡内容 hybrid——层级对齐场景）
3. ⏳ 自验收（手工正确实现跑通全部断言）
4. ⏳ 后台跑 4 项目 × 2 组
5. ⏳ 报告 + deepseek 端交叉验证邀请

## 七、诚实边界

- 预置卡为实验弹药——卡本身的开销不在统计内（与 T8/T9 口径一致：
  卡是资产非消耗品）
- 复杂度设计由 zcode 主观判定——需 deepseek 端复刻验证
- n=4 项目，结论为方向性观察
