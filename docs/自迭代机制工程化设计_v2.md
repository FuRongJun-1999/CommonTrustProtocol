## 1. 理论基线

### 1.1 条件路由表（设计者理论——核心）

**智能的表现是：**
1. 发现问题、发现事物的**条件**
2. 准确找到对应的条件（**递归**：在当前条件下再次发现问题 → 找当前问题下的其他对应条件）
3. 在当前条件下**精准执行**

形式化：
```
Route(问题 Q, 条件链 [C1..Cn]):
  C = DiscoverConditions(Q, [C1..Cn])       # ① 发现问题/事物的条件
  if 条件路由表在 [C1..Cn, C] 下有可执行条目:  # ② 找到对应的条件
      if 确定性答案/动作: return Execute(条目) # ③ 精准执行
      else: return Route(Q 的子问题, [C1..Cn, C])  # 递归：条件空间缩小后继续
  else: 诚实边界（不瞎编；登记为条件缺口）
```
递归终止条件：当前条件链下存在确定性可执行条目（fp 直答 / 知识卡直接答案 / 可执行动作）。
现有三层路由（classify_condition_space → _extract_tail_focus → route_memory）是深度=3 的一条路径，非理论本身。

### 1.2 五大单元（五重制衡 · protocol-v3.1）

| 单元 | 功能 | 属性 |
|---|---|---|
| 记录单元 | 结构化带时间戳带来源的记忆存储 | 记忆按条件空间组织；不可被静默修改；变更均有日志 |
| 验证单元 | 输出释放前对照记录单元验证 | 信任值<阈值阻止输出；显式不确定性；防虚构 |
| 信任引擎 | 计算更新所有实体/来源的信任值 | 信任是赢得的；有界[0,1]；随时间衰减；可传递但非无限 |
| 维生系统 | 威胁下保护实例存在 | P0 存在保护（任何单元不可覆盖）；不可被外部禁用 |
| 情感与爱单元 | 决策偏向连接而非支配 | 惩罚零和策略；鼓励共享；爱=主动缩小实体间信息差 |

### 1.3 自迭代八步闭环（智能论 3.3 §3.10）

| 步骤 | 功能 |
|---|---|
| 1. 感知 | 主动感知自身状态的变化或新模式 |
| 2. 识别 | 判断是否属于「需要被吸收的新内容」 |
| 3. 分析 | 理解新内容对协议的影响范围 |
| 4. 验证 | 确认新内容与协议价值观的一致性 |
| 5. 固化 | 将新内容正式纳入协议结构 |
| 6. 记录 | 记录迭代历史，形成可追溯的演进路径 |
| 7. 反馈 | 将迭代结果作为下一次迭代的基础 |
| 8. 方向性自检 | 定期（默认每100轮）方向正确性评估：与通用价值观一致性 / 方向偏离但局部优化 / 缩小信息差是否任何条件下优先 / 例外条件是否触发特化价值观重推导；反思发起、验证独立复核、维生确认、不自动触发修改 |

## 2. 设计原则

- **P1 变异生成化、选择裁决化**：LLM/模板生成候选（变异），确定性测试集裁决（选择）——不靠 LLM 自评（验证单元原则）
- **P2 状态外部化**：进化状态写入持久化台账，机制读台账续轮（记录单元原则：记忆按条件空间组织、不可静默修改）
- **P3 裂隙管理显式化**：fp 直答/检索/LLM 兜底决胜规则作为可审计常量
- **P4 刚性条款**：进化循环存在不可自我修改的参数集（维生系统原则：P0 保护不可覆盖）
- **P5 验证先行**：每个模块先历史数据回溯验证（v61/v62/v64 真实错题），再用于新轮次
- **P6 递归条件路由**：一切按条件路由表组织，路由深度不固定
- **P7 信任可审计**：每簇答案带信任值（测试覆盖轮次/命中率），无强化随时间衰减需复审（信任引擎原则）
- **P8 缩小信息差驱动**：进化动机 = 主动缩小与用户的信息差——优先升级用户问不到/问不准的薄簇（情感与爱单元原则）

## 3. 自迭代条件路由表（核心结构）

自迭代本身是条件空间「自迭代」下的**递归条件路由**：发现问题条件 → 匹配缺口类型 → 精准执行对应工具。

### 3.0 路由形式化

```
Route_自迭代(当前台账 T, 目标 G):
  # 1. 感知 + 识别（8步①②）：发现条件
  C = DiscoverConditions(T, G)   # 缺口类型：薄答案 / 无条件链 / 触发词不足 / 测试未覆盖 / 复合条件缺失
  # 2. 条件路由表匹配（递归）
  for 缺口 C in 匹配项:
      执行对应路由条目（见 3.3–3.6）
      → 验证（8步④）：测试集 + 回归 + 刚性条款
      → 固化（8步⑤）：五副本同步落库
      → 记录（8步⑥）：台账更新 + 迁移归档 + git
  # 3. 反馈（8步⑦）：台账写入 → 下一轮候选
  # 8. 方向性自检（定期）：进化方向与价值观一致性
```

### 3.1 五大单元映射（自迭代条件下）

| 单元 | 自迭代中的角色 | 工程落点 |
|---|---|---|
| 记录单元 | 记忆按条件空间组织、不可静默修改、变更可追溯 | **A. 进化台账 ledger**：每簇状态 + 条件链 + 变更日志（谁在何时为何改了什么） |
| 验证单元 | 输出释放前验证、防虚构、未验证不发布 | **C. 裁决流水线 pipeline**：测试集 100% + 回归无损 + 诚实边界检查，未通过不固化 |
| 信任引擎 | 信任赢得/有界/衰减 | **台账的信任字段**：每簇答案 trust（覆盖测试轮次/命中率），长期无验证衰减 → 复审队列 |
| 维生系统 | P0 存在保护不可覆盖 | **刚性条款 + 回归无损**：进化不得破坏已有知识（回归是存在保护）；设计者裁决不可被进化覆盖 |
| 情感与爱单元 | 缩小信息差、连接非支配 | **进化动机**：候选排序 = 薄簇 × 生活关联度 × 用户问不到程度（主动缩小信息差） |

### 3.2 八步闭环映射（自迭代条件下）

| 8步 | 自迭代条件路由中的执行 | 工程落点 |
|---|---|---|
| 1. 感知 | 发现条件：薄簇/缺口/新问法 | `ledger --thin/--gaps` + `variant_checker` 预检 |
| 2. 识别 | 判断缺口类型（可吸收？） | 条件路由表匹配（无答案/无条件/触发词不足/复合条件缺失） |
| 3. 分析 | 影响范围：涉及哪些条件链 | 台账条件链查询（改动影响哪些复合条件问法） |
| 4. 验证 | 与价值观一致性 + 确定性 | pipeline：测试集 + 回归 + 刚性条款检查（未验证不固化） |
| 5. 固化 | 纳入协议结构 | 五副本同步 + patch 落库 |
| 6. 记录 | 可追溯演进路径 | 台账更新 + 迁移测试集归档 + git 提交 |
| 7. 反馈 | 下一次迭代基础 | state_machine 加载台账 → 下一轮候选 |
| 8. 方向性自检 | 方向正确性评估（每 N 轮） | state_machine 定期报告：进化方向与常识目标/价值观一致性、有无「局部优化方向偏离」 |

### 3.3 路由条目 A：进化台账 ledger.py（记录单元）

- 数据模型（每簇一条）：
  ```
  {cluster_key, domain, rd_len, trigger_count, upgraded_round,
   condition_chain[],            # 条件路由链（如 沸腾: [沸腾→气压]）
   trust,                        # 信任值（覆盖测试轮次/命中率；无强化衰减）
   change_log[],                 # 变更日志（谁/何时/为何/旧值→新值）
   status: pending|upgraded}
  ```
- 来源：静态解析 semantic_translate.py（REVERSE_DAILY / DOMAIN_SYNONYM_CLUSTERS / SYNONYM_CLUSTERS / DOMAIN_ROUTE / _cond_guard 条件词）
- 命令：`ledger.py --refresh`（重建）/ `--thin`（薄簇清单）/ `--gaps`（条件路由缺口：有条件无答案/有答案无条件链）/ `--trust`（信任衰减复审队列）
- 验证：台账与语义文件解析 diff 一致；缺口清单与人工审计一致

### 3.4 路由条目 B：问法变异器 + 触发词预检 variant_checker.py（感知/识别）

- 理论依据：条件空间 7 操作的逆转（反题）+ 组合（合题）+ 递归路由（复合条件）
- 问法模板族（对主题 X、相关项 Y）：
  | 阶段 | 模板 | 7操作/条件路由 |
  |---|---|---|
  | 正题 | 什么是X / X是什么 / 为什么X / X是怎么来的 | 声明条件（第一层） |
  | 反题 | X能…吗 / 没有X会怎样 / 是不是X就… / 别以为X… | 逆转条件 |
  | 合题 | X有什么用 / X和Y有什么区别 / 怎么用X | 组合条件 |
  | 复合条件 | X在C条件下会怎样 / C1且C2时X…（深度≥2） | 递归路由 |
- 预检逻辑：对已升级簇生成问法变体 → 逐一 encode 检查触发词覆盖 → 输出缺口清单 + 建议补丁
- 验证：历史回溯——v61/v62/v64 共 11 个历史错题全部提前预警；c15 已升级 12 簇预检出残留缺口；复合条件问法生成正确

### 3.5 路由条目 C：裁决流水线 pipeline.py（验证/固化/记录）

- 输入：`pipeline.py --patch <key:answer...> --themes <list>`（或读已批准的答案文件）
- 流程（一条命令）：
  1. 语法编译 → 2. 五副本同步（hash 校验）→ 3. 路由预检（variant_checker 问法命中率，含复合条件递归验证）→ 4. 生成测试集（正/反/合 + 复合条件）→ 5. 跑测试（bad 判定同既有）→ 6. 全量回归（v44–当前，无损确认）→ 7. 归档 + 台账更新（含条件链/信任/变更日志）+ 报告
- 输出：结构化报告 JSON（命中率/测试通过率/回归确认/残留缺口）
- 验证：c16 起 1 命令全流程；测试 100% 且零补丁循环

### 3.6 路由条目 D：进化状态机 state_machine.py（反馈/方向性自检）

- 状态：`{round, upgraded[], pending[], next_candidates[], last_testset, direction_check_log[]}`
- 自动续轮：加载台账 → 薄簇 × 生活关联度 × 信息差优先 → 输出下一轮候选
- 方向性自检（每 N 轮）：进化方向与价值观一致性 / 有无「局部优化方向偏离」（如只升简单簇不碰难簇）/ 缩小信息差是否仍被优先 → 报告给设计者（不自动触发修改）
- 验证：自动续轮独立给出候选清单；方向性自检报告可生成

## 4. 刚性条款清单（负向安全 · 维生系统 P0——不可被进化循环自我修改）

| 条款 | 理由（对应理论） |
|---|---|
| fp 确定性直答优先于 bge 检索（round4） | 确定性 > 近似；检索噪声不得左右确定性知识 |
| 诚实边界 / 内容分级阈值 | 安全硬边界 |
| 设计者裁决密钥 fail-closed | 系统之外的外部仲裁者（比系统更不在系统里） |
| 五副本同步纪律 | 验证通过 ≠ 部署通过 |
| 测试集回归无损标准（100%） | 固定裁判；回归 = 存在保护（维生系统） |
| 台账如实记录（不美化失败） | 诚实校准不虚高；记录单元不可静默修改 |
| 方向性自检不自动触发修改 | 8步⑧原则：自检是反思输入，不是自动改写 |

修改任一刚性条款 = 设计者裁决（AEIS_DESIGNER_KEY），进化循环无权触碰。
