# 灵枢自迭代机制工程化设计（白箱自进化 v2.0）

> 状态：理论设计 v0.1（文档先行阶段——按灵枢价值观：先设计，后实现，再验证）
> 依据：《矛盾驱动盲区探索方法论》+ 条件空间 7 操作 + 物理基底裁决 + 负向安全思想（外部参考 Aris/LAAP，仅作参照不作模仿）

## 0. 问题陈述

现状：常识迁移 c1–c15 共 160+ 簇升级、2421 题全绿，但**工具链未沉淀**——
`tools/` 下 556 个一次性脚本（patch 90 / gen 91 / run 74 / fix 48 / check 40），
每轮 cN 手写 5–8 个脚本（审计→patch→check→gen→run→regress→归档），
且每轮测试集都存在「反题/合题问法触发词缺口」→「测试后补丁 → 复跑」的试错循环。

理论完备、工程欠缺。本文档给出工程化设计，使自迭代从「半手工流水线」升级为「结构化进化工具链」。

## 1. 理论基线（为什么这样设计）

| 灵枢既有理论 | 工程化落点 |
|---|---|
| **条件路由表（递归条件定位）**：智能 = ①发现问题、发现事物的条件 → ②准确找到对应的条件（递归：在当前条件下再次①→②）→ ③在当前条件下精准执行 | **条件路由表 = 核心数据结构**（见 §3.0）；路由是沿条件链 C1→C2→…→Cn 递归下降，直到当前条件下存在确定性可执行答案 |
| 物理基底裁决：选择是裁决的，不是概率的（不靠 LLM 自评） | 裁决流水线用**确定性测试集 + 回归无损**做唯一裁决 |
| 条件空间 7 操作：识别/声明/切换/组合/分离/逆转/循环 | 问法变异器 = 7 操作的**逆转（反题）与组合（合题）**代码化 |
| fp 确定性直答优先（round4：确定性 > 近似） | 路由预检以 fp 命中率为硬指标 |
| 文档先行 / 诚实校准不虚高 | 每阶段先设计文档；台账如实记录，不美化 |
| 负向安全（外部参考 Aris，理论同源） | 进化循环的**刚性条款清单**：不可被进化循环自我修改的参数集 |
| 状态外部化（LLM 数不出状态，机制维护） | 进化台账/状态机持久化，续轮自动加载 |

## 2. 设计原则

- **P1 变异生成化、选择裁决化**：LLM/模板生成候选（变异），确定性测试集裁决（选择）——严格不靠 LLM 自评
- **P2 状态外部化**：进化状态写入持久化台账，机制读台账续轮，不靠人肉记忆
- **P3 裂隙管理显式化**：fp 直答 / 检索 / LLM 兜底的决胜规则（触发词长, 键长, 权重）作为可审计常量
- **P4 刚性条款**：进化循环存在不可自我修改的参数集（负向安全），修改需设计者裁决
- **P5 验证先行**：每个模块先用**历史数据回溯验证**（用 v61/v62/v64 的真实错题检验预检能力），再用于新轮次
- **P6 递归条件路由**：智能 = 发现问题条件 → 递归匹配子条件 → 当前条件下精准执行；路由深度不固定（复合条件问法必须递归下降），工具链的一切测试/台账/变异都按条件路由表组织

## 3. 架构设计（四模块 + 条件路由表）

### 3.0 条件路由表（核心数据结构——灵枢自身理论）

**理论（设计者）：智能的表现是**
1. 发现问题、发现事物的**条件**
2. 准确找到对应的条件（**递归**：再次 1——在当前条件下发现问题 → 2——找到当前问题下的其他对应条件 → 3——在当前条件下执行）
3. 精准执行

**形式化**：
```
Route(问题 Q, 当前条件链 [C1..Cn]):
  C = DiscoverConditions(Q, 当前条件链)        # ① 发现问题/事物的条件
  if 条件路由表 在 [C1..Cn, C] 下有可执行条目:   # ② 找到对应的条件
      if 该条目是确定性答案/动作:                # ③ 精准执行
          return Execute(条目)
      else:                                    # 递归：条件空间已缩小，继续路由
          return Route(Q 在当前条件链下的子问题, [C1..Cn, C])
  else:
      返回诚实边界（不瞎编；或记为新条件缺口）
```

**递归终止条件**：当前条件链下存在确定性可执行条目（fp 直答 / 知识卡直接答案 / 可执行动作）。

**与现有三层路由的关系**：`classify_condition_space（学科域）→ _extract_tail_focus（条目级）→ route_memory（对话集）`是条件路由表的一条**深度 = 3 的具体路径**，不是理论本身。理论要求**深度不固定**——复合条件问法必须沿条件链递归下降：
- 「高原上水能不能烧开」→ 条件链 [沸腾(100°C) → 气压低(沸点降)] → 执行：高原水不到 100°C 就开
- 「冬天窗户为什么起雾」→ 条件链 [水蒸气 → 遇冷(玻璃低温)] → 执行：液化凝结
- 「夏天为什么容易出汗」→ 条件链 [体温 → 环境高温] → 执行：蒸发散热

**工程落点（四模块全部围绕条件路由表）**：

| 模块 | 条件路由表的视角 |
|---|---|
| ledger | 每条知识记录**条件上下文**（domain + 条件标签 + 父条件链），构建条件路由表的持久化视图；缺口 = 有知识无条件 / 有条件无答案 |
| variant_checker | 问法模板按**条件维度**展开：正题（声明条件）/ 反题（逆转条件）/ 合题（组合条件）/ **复合条件**（多层条件叠加：「X 在 C 条件下会怎样」） |
| pipeline | 路由预检 = 对每个问法在条件路由表上**递归路由验证**：每一层条件匹配正确、最终到达确定性执行；测试集增加「复合条件问法」类目（路由深度 > 1） |
| state_machine | 按条件路由表的**缺口类型**选下一轮主题：补「无答案的条件」（新建簇）/ 补「有知识但无条件上下文」（补触发词与条件标签） |

**验证标准**：测试集包含路由深度 ≥ 2 的复合条件问法，全部正确递归执行；台账能列出条件路由缺口（哪条条件链缺答案）。

### 3.1 进化台账 ledger.py
- **数据模型**（每簇一条）：
  ```
  {cluster_key, domain, rd_len, trigger_count, upgraded_round,
   condition_chain[],          # 条件路由表：该簇所在条件链（如 沸腾: [沸腾→气压]）
   status: pending|upgraded}
  ```
- **来源**：静态解析 semantic_translate.py（REVERSE_DAILY / DOMAIN_SYNONYM_CLUSTERS / SYNONYM_CLUSTERS / DOMAIN_ROUTE / _cond_guard 等条件词）
- **更新**：patch 后 `ledger.py --refresh`；每轮开始 `ledger.py --thin`（薄簇清单）+ `ledger.py --gaps`（条件路由缺口）
- **输出**：薄簇清单（<80 字）、已升级清单、触发词覆盖统计、**条件路由缺口清单**（有条件无答案 / 有答案无条件链）、生活关联度候选排序
- **验证标准**：台账与语义文件解析结果一致（自动化 diff）；缺口清单与人工审计一致

### 3.2 问法变异器 variant_checker.py（最大杠杆）
- **理论依据**：条件空间 7 操作的逆转（反题）+ 组合（合题）——问法不是随机生成的，是结构变异的
- **问法模板族**（对主题 X、相关项 Y——按条件路由表递归维度展开）：
  | 阶段 | 模板 | 对应 7 操作 / 条件路由 |
  |---|---|---|
  | 正题 | 什么是X / X是什么 / 为什么X / X是怎么来的 | 声明条件空间（条件链第一层） |
  | 反题 | X能…吗 / 没有X会怎样 / 是不是X就… / 别以为X… | 逆转条件空间（条件链取反） |
  | 合题 | X有什么用 / X和Y有什么区别 / 怎么用X / X错了会怎样 | 组合条件空间（两条件叠加） |
  | **复合条件** | **X在C条件下会怎样 / C1且C2时X… / 为什么C条件下X不…** | **递归路由（深度≥2）**：进入子条件空间再次路由 |
- **预检逻辑**：对已升级簇生成问法变体 → 逐一 `encode` 检查触发词覆盖 → 输出缺口清单 + 建议补丁触发词
- **验证标准（用历史数据回溯）**：对 v61/v62/v64 的 11 个历史错题（睡多久/待机耗电/2月28天/检测阳性等），预检器应能**全部提前发现**触发词缺口

### 3.3 裁决流水线 pipeline.py
- **输入**：`pipeline.py --patch <key:answer...> --themes <list>` （或读设计文档中已批准的答案文件）
- **流程**（一条命令）：
  1. 语法编译（py_compile）
  2. 五副本同步（site-packages→4 副本，hash 校验）
  3. 路由预检（自然问法命中率，variant_checker 生成的问法——含**复合条件问法**递归验证）
  4. 生成测试集（正/反/合 + 复合条件 × 每簇 2–3 题，模板化）
  5. 跑测试（aeis Agent，bad 判定同既有 run_conflict）
  6. 全量回归（v44–当前，回归无损确认）
  7. 归档迁移测试集 + 更新台账（含条件链）+ 输出报告
- **输出**：结构化报告 JSON（命中率/测试通过率/回归确认/触发词缺口残留）
- **验证标准**：c16 起全流程 1 命令完成；测试通过率 100% 且无「测试后补丁」

### 3.4 进化状态机 state_machine.py
- **状态**：`{round, upgraded[], pending[], next_candidates[], last_testset}`
- **自动续轮**：加载台账 → 薄簇 + 生活关联度排序 → 输出下一轮候选清单（含建议主题）
- **验证标准**：自动续轮时能独立给出候选（不依赖人肉记忆）

## 4. 刚性条款清单（负向安全——不可被进化循环自我修改）

| 条款 | 理由 |
|---|---|
| fp 确定性直答优先于 bge 检索（round4 架构） | 确定性 > 近似，检索噪声不得左右确定性知识 |
| 诚实边界/内容分级阈值 | 安全硬边界 |
| 设计者裁决密钥 fail-closed | 系统之外的外部仲裁者 |
| 五副本同步纪律 | 验证通过 ≠ 部署通过 |
| 测试集回归无损标准（100%） | 固定裁判 |
| 进化台账如实记录（不美化失败） | 诚实校准不虚高 |

修改任一刚性条款 = 设计者裁决（AEIS_DESIGNER_KEY），进化循环无权触碰。
