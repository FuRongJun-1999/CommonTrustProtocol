## 一、语法树不稀奇——条件路由图本身就是（条件化）语法树

判断：**语法树不是稀奇的东西**。我们的条件路由图本质上也是语法树——只是它的「语法」是**条件化语法**（条件词 → 节点 → 条件边），不是编程语言的词法语法。

> **精确本身就是条件化语法要求**：把图的「精确」补上 = 把条件化语法完备化——
> 每个条件词的边界、每个节点的资格判定、每条边的适用条件都要可精确判定，
> 这正是「精确 = 条件化语法要求」的含义。CodeGraph 的语法树精确来自 tree-sitter 的
> 严格文法；我们的条件路由图精确来自条件空间的严格声明（KCCS 四要素 + 四态判定）。

**含义**：不需要引入 tree-sitter 学它的语法树——我们的条件路由图在「条件语义层」天然高于语法树（语法树只回答「有什么结构」，条件图回答「在什么条件下成立」）。要补的是**精确度**（条件化语法的完备与歧义消除），不是结构类型。

## 二、语言覆盖：只做四门（Python / Rust / JS / 中文编译）

**不做 38 语言覆盖**——那是 CodeGraph 的护城河，不是我们的。

| 语言 | 我们的现状 | 定位 |
|---|---|---|
| Python | 681 单元主战场、生态本体 | 主语言 |
| Rust | codegraph-ref 审查样本（0.9012 评分经验）| 系统层/性能层（蜂群、底层工具）|
| JS/TS | dsh-memory 插件本体 | Agent 生态层 |
| 中文编译 | protocol-compiler（词法/语法/字节码 VM 全链路）| 自举核心 |

四门语言对齐灵枢真实运行环境（Python 本体 / Rust 底层 / JS 插件 / 中文协议），不追广度。

## 三、生态：引入 MCP 与 VS Code 工具——本地编译运行是极强的补全

**当前缺陷**：我们「物理基底校准」理念有（测试用例实际运行），但**代码侧执行能力缺工具化**——
CodeGraph 有 42 MCP 工具 + VS Code 扩展，我们没有成型的代码执行工具链。

**方向**：
- **引入 MCP 工具**：代码执行类 MCP（本地编译/运行/测试），让「物理基底裁决」在 agent 工作流里一键可用
- **引入 VS Code 工具**：编辑器的实时校验/单步执行——「能直接本地编译运行」是把物理基底从理念变成日常操作的补全
- 这与「条件路由图精确化」闭环：**图给出条件与规则，本地执行给出物理裁决**——两者结合才是完整白箱。

## 四、代码库 = 灵枢自举 + 开源规范自然补全

**判断**：代码库（知识单元、注释、工具）本质是**灵枢自举的产物**——不是预先建好的百科全书，而是白箱自举（六阶段已实证：从条件单元库到中文编译器）生长出来的。

**含义**：
- 我们提供**规范**（KCCS 注释规范 / WB-SPEC 八维 / 条件路由图结构）
- **开源自然会补全**——与「闭源防抄袭最愚蠢，开源扩散减少信息差」立场一致：规范开放，贡献者按规范补全各语言/各领域的单元
- 不追求「我们亲手写完全部语言」——追求「规范足够好，让补全自然发生」
